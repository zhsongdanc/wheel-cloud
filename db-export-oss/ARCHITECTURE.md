# db-export-oss Architecture Notes

## 模块目标

这个模块目前更像一个业务工具型模块，适合用来学习：

- 模块边界划分
- SDK / Service 的职责设计
- 面向扩展的导出能力抽象
- 工程化与复用

虽然它看上去不像典型的分布式模块，但很适合练习“业务能力如何演进成可复用组件”。

## 值得先思考的问题

- 这是一个业务模块，还是一个可复用组件？
- 导出能力的稳定边界应该是什么？
- 数据库类型差异应不应该泄露到调用方？
- 如果后续支持多种存储、多种导出格式，哪些地方最容易失控？

## 核心设计思想

### 1. 先定义边界，再堆功能

很多工具型模块后期会变乱，往往不是功能太多，而是边界不清：

- 谁负责准备数据？
- 谁负责导出格式转换？
- 谁负责上传到 OSS？
- 谁负责失败补偿和重试？

### 2. 抽象要围绕变化点

如果未来会扩展：

- 多数据库类型
- 多导出格式
- 多存储后端

那抽象应该围绕这些变化点展开，而不是围绕当前一次性的实现细节展开。

### 3. 工程化能力本身也是架构的一部分

这个模块虽然不像 RPC 或注册中心那样“分布式味”很浓，但它很适合练习：

- 接口抽象
- 策略模式
- 模板方法
- 可测试性
- 错误处理和可观测性

## 当前模块定位

从现有文件看，当前核心点还比较集中：

- `ExportSDKService`
- `DbType`

这意味着它非常适合后续边实现边抽象，逐步把能力沉淀清楚。
