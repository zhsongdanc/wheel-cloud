# real-cloud-eureka Architecture Notes

## 模块目标

这个模块适合学习微服务最基础的一层能力：

- 服务注册
- 服务发现
- 服务实例管理
- 心跳与健康检查

很多人一开始把 Eureka 理解成“一个注册表”，但它真正重要的是让服务从“写死地址”演进到“动态寻址”。

## 值得先思考的问题

- 如果服务地址写死在配置里，扩容、缩容、迁移时会发生什么？
- 为什么微服务体系里“找到服务”本身就是一个基础能力？
- 客户端发现和服务端发现分别意味着什么？
- 注册中心为什么通常会容忍短时间不一致？

## 核心设计思想

### 1. 服务不是固定机器，而是一组动态实例

微服务环境里，服务本质上不是一台机器，而是一组会变化的实例集合。注册中心的意义，就是把“服务名 -> 实例列表”的映射维护起来。

### 2. 先解耦寻址，再谈治理

如果连服务都找不到，后面的负载均衡、熔断、重试、灰度发布都无从谈起。所以注册发现是很多分布式治理能力的起点。

### 3. AP 取向的现实权衡

Eureka 常被拿来讨论 CAP 中偏 AP 的设计思路。值得思考：

- 为什么它会更重视可用性，而不是强一致？
- 在注册中心短时间数据不一致时，业务是否还能继续？
- 这种选择更适合哪类场景？

## 后续记录区

### 设计思想记录

- 第一版采用 `serviceName -> instanceId -> Lease<InstanceInfo>` 的内存模型，而不是直接存实例列表
- `InstanceInfo` 表达“这个实例是谁”，`Lease` 表达“它最近一次证明自己活着是什么时候”
- 注册、续约和剔除被拆成不同职责：客户端负责主动上报，服务端负责超时清理
- 过期处理采用后台 `eviction task`，而不是把清理逻辑下放到查询链路中

### 第一阶段实现范围

- 注册实例
- 心跳续约
- 查询某个服务的实例列表
- 查看整个注册表快照
- 后台定时剔除过期实例
- 主动注销接口作为辅助能力保留
- 在同一个 Maven 模块里按 3 个角色组织学习代码：`registry`、`provider`、`consumer`

### 当前代码骨架

- `RegistryProperties`：统一管理 lease 和清理周期等配置
- `InstanceInfo`：实例基础信息
- `Lease`：实例租约与续约时间
- `InMemoryRegistry`：内存注册表核心逻辑
- `RegistryController`：教学版 server API
- `EvictionTask`：后台过期清理任务
- `EurekaLikeClient`：学习版 client，负责注册、续约、后台拉取注册表和本地缓存
- `ProviderDemoController`：最小 provider，证明注册表里的地址最终会进入真实调用
- `ConsumerController` / `ConsumerService`：最小 consumer，从本地缓存选 provider 并发起调用

### 问题分析记录

- 为什么不能只依赖主动注销：
  真实场景里大量下线来自宕机、断网、强杀，服务来不及发 `unregister`
- 为什么需要 lease：
  注册中心往往拿不到“死亡通知”，只能基于“长时间没有续约”做失效判断
- 为什么需要 eviction：
  心跳只负责刷新存活状态，不会自动把脏实例从注册表删除
- Eureka 更偏向“服务端定时扫描并剔除过期实例”，而不是“每次请求进来时顺手下线过期实例”
  - 这样做的核心原因是把“写路径/读路径”和“清理路径”分开
  - 注册、续约、查询这些主链路尽量保持简单，不在每次请求里混入全表或局部清理逻辑
  - 过期实例的下线由后台 `eviction task` 周期性处理，这是一种集中式兜底清理
  - 查询时当然也可以做过滤保护，但那更像补充策略，不是注册中心清理脏数据的主机制
- 关于“为什么不是请求触发删除，而是定时扫描”的更核心表述
  - 请求触发删除会直接污染服务发现接口的响应时间，让 `Latency` 变得不可控；服务规模一大，请求路径里夹带清理逻辑，Eureka Server 很容易变成整个微服务集群的单点性能瓶颈
  - 定时扫描的本质收益是把“维护注册表”和“查询注册表”彻底解耦；查询只读当前内存注册表，路径短、开销稳定、性能上限更高
  - 如果把服务发现设计成实时查注册中心，调用链会退化成 `Client -> Eureka -> Client -> Provider` 的 3 跳模型，多出一次 RTT；在高性能场景里，这个额外网络往返成本通常不可接受
  - 即使不考虑自我保护、本地缓存这些增强机制，只从最小架构原则看，请求时删除也会让注册中心同时背负“查询入口 + 清理入口”的双重压力，削弱整个系统的故障容错能力
- 关于“为什么客户端要缓存注册表，而不是请求来了再查”的更核心表述
  - Eureka 的关键目标，是把注册中心从业务调用主链路中拿掉，让它退化成控制面组件，而不是每次请求都要经过的数据面组件
  - 如果采用“缓存过期了，请求线程现场去拉”的模式，请求延迟会直接绑定注册中心的响应时间，业务 RT 变得不可控
  - 一旦多个客户端缓存同时过期，请求到来时集体回源拉取注册表，会把 Eureka 推成瞬时流量热点，造成明显的放大效应
  - 更合理的方式是：业务请求线程只读本地缓存，后台线程定时更新缓存；允许短时间旧数据存在，换取调用链稳定性和系统容错能力
  - 全量拉取和增量拉取的区别，不在“能不能同步”，而在“同步成本”：
    全量拉取实现简单，但注册表大时传输和反序列化成本高；增量拉取只同步变化部分，更适合大规模服务场景
- 关于“什么时候增量更新，什么时候全量更新”的更核心表述
  - 正常情况下优先增量更新，因为增量更新的目标是降低同步成本：只拉变化部分，减轻网络、序列化和 Eureka Server 压力
  - 增量更新成立的前提是“客户端当前缓存仍然可信”，也就是客户端和服务端之间有连续的版本基础，没有断档
  - 当客户端首次启动、本地没有缓存、增量同步失败、版本对不上、怀疑本地漏掉一段变更时，就应该回退到全量更新
  - 全量更新不是为了更高效，而是为了重新建立一份可信的注册表基线；它解决的是“正确性恢复”问题，不是“同步效率”问题
  - 一句话看：增量更新依赖旧数据可信，全量更新负责重建可信基础
- 关于 `AtomicReference<ClientRegistrySnapshot>` 的核心理解
  - 它保护的重点不是“对象内部字段怎么改”，而是“当前缓存引用指向哪一个快照版本”
  - `AtomicReference.set(newSnapshot)` 的线程安全，本质上来自对“引用替换”这件事的原子性和可见性保证
  - 它能保证读线程看到的是“旧快照 A”或“新快照 B”，而不是一个“切换到一半”的引用状态
  - 它不负责保护 `newSnapshot` 内部数据结构的并发修改；它保护的是“对象身份切换”，不是“对象内部状态变化”
  - 在 Eureka client 这种本地缓存模型里，它特别适合表达“先构造完整新快照，再整体切换缓存版本”的语义
- 关于“第一版 client 为什么先做后台全量拉取”的更核心表述
  - 第一版先做全量拉取，不是因为它更先进，而是因为它能把 Eureka client 最核心的后台任务模型先跑通：注册、续约、本地缓存、异步刷新
  - 当前阶段最重要的是先证明“请求线程不直接查注册中心”，而不是过早陷入增量同步、版本号和断档恢复这些复杂问题
  - 等后台全量拉取链路稳定后，再引入增量拉取，才能真正看清楚“增量是效率优化，不是架构主干”
- 关于“为什么要在同一模块里拆出 registry/provider/consumer 三个角色”的更核心表述
  - 只看 `Eureka + 自注册 client`，你只能学到注册和缓存，学不到“服务发现结果如何进入真实业务调用链”
  - 拆出三个角色后，链路才完整：`provider` 注册自己，`consumer` 拉本地缓存，再根据缓存地址去调 `provider`
  - 这样既保留了单模块学习项目的低复杂度，又能把控制面和数据面关系讲清楚
