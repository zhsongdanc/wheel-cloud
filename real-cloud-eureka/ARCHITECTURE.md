# real-cloud-eureka Architecture Notes

## 模块目标

这个模块适合学习微服务最基础的一层能力：

- 服务注册
- 服务发现
- 服务实例管理
- 心跳与健康检查

很多人一开始把 Eureka 理解成“一个注册表”，但它真正重要的是让服务从“写死地址”演进到“动态寻址”。

## 值得先思考的问题

- 如果服务地址写死在配置里，扩容、缩容、迁移时会发生什么？
- 为什么微服务体系里“找到服务”本身就是一个基础能力？
- 客户端发现和服务端发现分别意味着什么？
- 注册中心为什么通常会容忍短时间不一致？

## 核心设计思想

### 1. 服务不是固定机器，而是一组动态实例

微服务环境里，服务本质上不是一台机器，而是一组会变化的实例集合。注册中心的意义，就是把“服务名 -> 实例列表”的映射维护起来。

### 2. 先解耦寻址，再谈治理

如果连服务都找不到，后面的负载均衡、熔断、重试、灰度发布都无从谈起。所以注册发现是很多分布式治理能力的起点。

### 3. AP 取向的现实权衡

Eureka 常被拿来讨论 CAP 中偏 AP 的设计思路。值得思考：

- 为什么它会更重视可用性，而不是强一致？
- 在注册中心短时间数据不一致时，业务是否还能继续？
- 这种选择更适合哪类场景？

## 后续记录区

### 设计思想记录

- 第一版采用 `serviceName -> instanceId -> Lease<InstanceInfo>` 的内存模型，而不是直接存实例列表
- `InstanceInfo` 表达“这个实例是谁”，`Lease` 表达“它最近一次证明自己活着是什么时候”
- 注册、续约和剔除被拆成不同职责：客户端负责主动上报，服务端负责超时清理
- 过期处理采用后台 `eviction task`，而不是把清理逻辑下放到查询链路中

### 第一阶段实现范围

- 注册实例
- 心跳续约
- 查询某个服务的实例列表
- 查看整个注册表快照
- 后台定时剔除过期实例
- 主动注销接口作为辅助能力保留

### 当前代码骨架

- `RegistryProperties`：统一管理 lease 和清理周期等配置
- `InstanceInfo`：实例基础信息
- `Lease`：实例租约与续约时间
- `InMemoryRegistry`：内存注册表核心逻辑
- `RegistryController`：教学版 server API
- `EvictionTask`：后台过期清理任务

### 问题分析记录

- 为什么不能只依赖主动注销：
  真实场景里大量下线来自宕机、断网、强杀，服务来不及发 `unregister`
- 为什么需要 lease：
  注册中心往往拿不到“死亡通知”，只能基于“长时间没有续约”做失效判断
- 为什么需要 eviction：
  心跳只负责刷新存活状态，不会自动把脏实例从注册表删除
