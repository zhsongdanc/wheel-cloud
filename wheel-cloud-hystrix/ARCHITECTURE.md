# wheel-cloud-hystrix Architecture Notes

## 模块目标

这个模块适合用来学习服务治理中的核心能力：

- 熔断
- 限流
- 隔离
- 降级
- 失败统计与状态切换

它的学习价值不只是“模仿 Hystrix”，而是理解这些机制为什么会在分布式系统中出现。

## 当前实现观察

从当前代码结构看，这个模块已经覆盖了不少关键点：

- 注解驱动入口：`HystrixCommand`、`RateLimit`
- 属性解析：`CommandParser`、`HystrixProperty`
- 调用隔离：线程池隔离、信号量隔离
- 熔断状态管理：`CircuitBreaker`、`CircuitBreakerManager`
- 限流算法：固定窗口、滑动窗口、漏桶、令牌桶
- 统计分析：`BucketManager`
- Spring 扩展点：后置处理器、拦截器、配置类

这很适合拿来学习“治理框架”的骨架设计。

## 核心设计思想

### 1. 为什么服务治理要前置到框架层

值得先想的问题：

- 为什么不能在每个业务方法里手写 `try-catch` 和失败重试？
- 为什么限流/熔断逻辑不应该散落在业务代码里？
- 如果没有统一框架，多个服务团队的治理策略如何一致？

这里的核心思想通常是：

- 把横切能力抽到统一框架层
- 让业务代码只关注业务语义
- 让治理策略具备可配置、可复用、可观测能力

### 2. 为什么要有隔离

值得追问：

- 一个下游接口变慢，为什么会上游线程池耗尽？
- 为什么“失败”比“慢”更容易被发现，而“慢”更危险？
- 线程池隔离和信号量隔离分别在保护什么？

### 3. 为什么要有熔断

值得追问：

- 当下游已经持续失败时，为什么还要继续请求它？
- 熔断到底是在保护调用方，还是保护被调用方？
- 半开状态为什么存在？

### 4. 为什么要有统计窗口

值得追问：

- 为什么熔断通常不是基于单次请求决定？
- 为什么限流统计会涉及固定窗口、滑动窗口、桶拆分？
- 统计粒度越细越好吗？

## 适合继续深挖的方向

- 注解 + 代理 + 拦截器是怎样把治理逻辑织入业务方法的
- 统计窗口的时间精度和性能之间如何权衡
- 熔断状态机如何设计得更稳定
- 限流算法分别适合保护瞬时流量还是平滑流量
- 如果迁移到 Spring Cloud Alibaba Sentinel，设计思想哪些相同，哪些不同
